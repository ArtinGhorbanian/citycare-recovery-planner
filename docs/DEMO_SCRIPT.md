# Local Demonstration Script

## Purpose

This script supports an internal, local demonstration using repository-generated synthetic data. It is designed to explain the workflow and its limitations, not to simulate a real emergency or claim medical/operational effectiveness.

Suggested duration: 8-10 minutes.

## Preflight

Run these commands from the repository root in an isolated Python environment:

```text
python -m pip install -r requirements.lock
python scripts/generate_citycare_demo_data.py --force
```

Copy `.env.example` to `.env`, then confirm:

```text
DATASET_PATH=data/citycare_demo_dataset.csv
HOST=127.0.0.1
DEBUG=false
AI_ENABLED=false
```

Start the application:

```text
python app.py
```

Open the loopback URL printed in the terminal. Do not use the demonstration with confidential, patient, or real-hospital data. Do not bind it to a shared/public interface.

## 0:00-1:00 - Frame the prototype

Show Dataset Overview.

Suggested narration:

> This is a local decision-support prototype running on deterministic synthetic scenarios. It is not connected to a hospital, does not contain real patients, and is not medical advice. The models predict fields defined by the demo CSV over a two-hour horizon; qualified people would have to verify every input and decision in any real setting.

Point out the row count, hospital count, time period, status distribution, and visible limitations. Avoid calling these values live, actual, or representative.

## 1:00-2:00 - Explain model evidence

Open Model Quality.

Show:

- the chronological training/testing periods and zero shared timestamps;
- per-target R-squared and mean absolute error;
- classifier accuracy, macro F1, confusion matrix, and per-class recall;
- feature importance; and
- excluded target columns.

Suggested narration:

> These metrics describe one configured synthetic dataset and a later chronological test partition. They are useful for checking the implementation, but they are not external or clinical validation. Feature importance is global forest importance, not causality.

## 2:00-3:15 - Build a scenario

Open Crisis Situation. Keep the first hospital's latest demo record or select another hospital.

Change one or two fields, for example:

- increase bed occupancy;
- increase ambulance arrivals; or
- reduce the nurse-to-patient ratio.

Select **Analyze Crisis and Build Recovery Plan**.

Suggested narration:

> The browser sends one validated snapshot. Values outside the model's observed training range are allowed but explicitly warned. Negative, non-finite, unknown-category, and incorrectly scaled rate inputs are rejected by the server.

## 3:15-4:45 - Read prediction results carefully

Show Prediction Results and identify:

- patients expected over the next two hours;
- estimated ICU beds, ventilators, and staff units;
- overload risk and capacity status;
- the tree-dispersion ranges;
- the resilience formula;
- pressure factors and similar demo records; and
- the rule-based briefing tag.

Suggested narration:

> The ranges are the 10th and 90th percentiles across trees, not calibrated confidence intervals. The resilience index is a transparent project formula, not a validated medical score. Similar rows are dataset comparisons, not a claim that two incidents are equivalent.

If a warning appears, read it aloud rather than dismissing it.

## 4:45-5:45 - Show actions and decision points

Open Recovery Strategies and then Decision Points.

Suggested narration:

> These sentences are generated by fixed operational rules from the displayed model values. They deliberately use cautious language. Possible coordination hospitals only have lower modeled pressure under the coded criteria; capacity, transport, transfer eligibility, and local procedures are not verified.

Point to the coordination caveat and qualified-review requirement.

## 5:45-7:15 - Allocate a limited reserve

Open Emergency Reserve and enter small whole-number reserves, for example:

- 12 ICU beds;
- 8 ventilators; and
- 25 staff units.

Keep the current scenario enabled. Adjust a priority slider, then select **Build Allocation Plan**.

Show the Allocation Report totals, remaining reserve, selected-hospital row, ranking, expandable detail, and method explanation.

Suggested narration:

> The planner distributes only the reserve entered here. It does not know total hospital inventory or calculate an exact shortage. Each resource is constrained so the total cannot exceed the entered reserve and a hospital cannot receive more than its rounded estimated need.

Do not describe staff units as doctors; the data does not establish that those units are equivalent.

## 7:15-8:00 - Demonstrate stale-state protection

Return to Emergency Reserve, change one reserve value, and revisit Allocation Report.

Point out the stale notice and disabled CSV download. Then change a Step 1 scenario field and show that the prediction state also becomes stale.

Suggested narration:

> A result remains visible for comparison, but the interface does not silently present it as current. The operator must recalculate before downloading or using downstream results.

## 8:00-9:00 - Reference views and assistant

Open Resilience & Trends. Explain that weekly values are aggregates from the demo CSV and direction is a simple slope over at most 12 points, not a long-range forecast.

Open Assistant and select **What are the limitations?**

Suggested narration:

> The assistant is in fixed-rule mode, so this request remains inside the application. If external AI wording were enabled, the question and relevant operational/model context could leave the process. There is no sensitive-data redaction, so AI stays off for this demo.

## Close

Suggested closing statement:

> The useful result of this prototype is an inspectable workflow: explicit inputs, time-aware test metrics, bounded predictions, transparent heuristics, constrained reserve allocation, stale-result handling, and visible limitations. It remains a local engineering artifact. Real use would require governed representative data, independent validation, authenticated production infrastructure, verified live integrations, monitoring, and qualified safety, privacy, legal, clinical, and operational review.

## Demonstration guardrails

Do not:

- load or mention a separately supplied dataset unless its use is explicitly authorized;
- enter names, identifiers, patient details, real capacity, or confidential incident information;
- enable AI without an approved egress review;
- call tree ranges confidence intervals;
- call the resilience or priority score medically validated;
- imply that a coordination candidate has confirmed capacity;
- state that reserve allocation changes real resources;
- expose the Flask port to a shared/public network; or
- describe the prototype as production-ready.

## Troubleshooting

| Symptom | Check |
| --- | --- |
| Startup status is unavailable | Confirm `.env`, `DATASET_PATH`, generator output, file permissions, and required columns. |
| Generated file already exists | Use `--force` only when intentionally replacing the local synthetic file. |
| A view is locked | Run the prerequisite prediction or allocation step. |
| A result is stale | Re-run the analysis/allocation after the last input change. |
| Charts do not appear | Use the adjacent data tables and confirm `static/vendor/chart.umd.js` exists. |
| Assistant says AI was not used | This is expected with `AI_ENABLED=false`; fixed-rule content remains available. |

## After the demo

Stop the Flask process. The application itself does not persist form state, chat, models, or results, but any browser downloads and the generated local CSV remain on disk until handled according to local policy.
